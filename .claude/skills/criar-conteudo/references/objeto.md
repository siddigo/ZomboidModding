# Objeto — a pilha dentro da pilha

**Contrato completo em duas partes da doc:**

- **Tile** — `Documentacao/jogo/tiles.md`: os três artefatos acoplados, a forma do `.tiles.txt`, e o
  fato de que **nem todo `.tiles` tem par de texto** (7 binários para 5 `.tiles.txt`).
- **`entity` e `xuiSkin`** — `Documentacao/jogo/scripts-txt.md`, seções correspondentes.

Esta página carrega o enquadramento — que é o que a doc não tem, porque não é sobre o jogo, é sobre
como decidir o trabalho.

## Três camadas, não três opções

"Criar objeto" parece três coisas diferentes e é **uma só, em camadas**. Não são alternativas: um
objeto completo tem as três, e objetos mais simples param antes.

| Camada | Quando é necessária | Formato |
|---|---|---|
| **1. Tile** | sempre — é o que faz existir no mundo | `.tiles` (+ `.tiles.txt`) + `.pack` |
| **2. Moveable** | se o jogador **pega e larga** | `item` com `ItemType = base:moveable` |
| **3. Entity** | se o jogador **usa** (bancada, forno, estação) | `entity` + `component` |

Exemplos: bancada de ferraria = 1+2+3. Armário decorativo = só 1. Fogueira que não se carrega = 1+3.

**Decida com o usuário até onde vai antes de escrever.** É a pergunta que define o tamanho do
trabalho — e muda se ele vai precisar de ferramenta externa ou não.

## A primeira pergunta: dá para reusar sprite do jogo?

**Pergunte isso antes de qualquer outra coisa.** Se o objeto novo puder usar um sprite que já existe
em `PZ/media/`, a camada 1 desaparece e o trabalho fica inteiro dentro do que esta skill fecha —
`entity` e/ou `moveable`, tudo `.txt`.

Se precisar de arte de mundo nova, ver o limite abaixo.

## O limite honesto

**O `.tiles` binário e o `.pack` não saem daqui.** São saída do TileZed, e `tiles.md` registra que a
ferramenta nem está no `PZ/` — só há prova de que foi usada (13 `.lua` do jogo abrem com
`-- THIS FILE WAS AUTOMATICALLY GENERATED BY TileZed`).

O que dá para fazer: escrever/editar o `.tiles.txt`, nomear os sprites corretamente, e escrever as
camadas 2 e 3 já apontando para os nomes combinados. O que **não** dá: fechar o ciclo.

Diga isso no relatório. E note o que `tiles.md` deixa em aberto: se o `.tiles` binário torna o
`.tiles.txt` dispensável na distribuição de um mod ainda é inferência, não fato.

## Camada 2 — moveable

Item comum com `ItemType = base:moveable`. Ver `item.md`. A diferença é que ele referencia o sprite
do mundo, não só um ícone de inventário.

Tradução vai em `Moveables.json`, não `ItemName.json` — ver `traducao.md`.

## Camada 3 — entity, lado-mod

O que a doc mostra é o bloco do jogo. Lado-mod, o que importa:

```
module MeuMod
{
    entity MinhaBancada
    {
        component SpriteConfig
        {
            face S { layer { row = meutileset_01_0 meutileset_01_1, } }
            face E { layer { row = meutileset_01_2, row = meutileset_01_3, } }
        }
        component CraftRecipe
        {
            time = 10,
            category = Carpentry,
            inputs
            {
                item 2 [Base.Plank],
                item 4 [Base.Nails],
            }
        }
    }
}
```

- **`SpriteConfig` é o que amarra a camada 3 na camada 1.** Os nomes em `row` são nomes de sprite do
  tileset (`<file>_<índice>`, o índice vindo do `xy` na grade — ver `tiles.md`). **Sprite que não
  existe = entidade invisível, sem erro no console.**
- `component CraftRecipe` aqui é a **receita de construção da própria entidade** — mesma sintaxe de
  `inputs`, **sem `outputs`** (a saída é a entidade). Receitas que a bancada *hospeda* são
  `craftRecipe` normais, amarradas por `category`/tag — coisa diferente, ver `receita.md`.

### `xuiSkin` — só se a entidade abre janela

Bloco separado, em `media/scripts/entities/`. Use `LuaWindowClass = ISEntityWindow` (a genérica) a
menos que o mod traga classe Lua própria.

## L3 para objeto

Objeto com tile próprio ganha loot próprio por `forceForTiles`, o campo que amarra distribuição a nome
de sprite. Ver `mundo.md` e `Documentacao/jogo/distribuicao-loot.md`.
