# Tiles — os artefatos acoplados e o TileZed

O que são os arquivos de tile na raiz de `media/`, como se relacionam, e qual deles sai de
ferramenta externa. Página de **localização e acoplamento**; não é tutorial de mapa.

Alias `PZ/` = `C:\Program Files (x86)\Steam\steamapps\common\ProjectZomboid\`.

## Três artefatos, não um par

Um tileset só funciona com três coisas em lugares diferentes:

| Artefato | Onde | Formato | Tamanho típico |
|---|---|---|---|
| `*.tiles` | raiz de `PZ/media/` | **binário** — magic `tdef\x01` | 2,9 MB (`newtiledefinitions`) |
| `*.tiles.txt` | raiz de `PZ/media/` | texto | 6,8 MB (o mesmo tileset) |
| `texturepacks/*.pack` | `PZ/media/texturepacks/` | binário, atlas de sprite | 24 arquivos |

O `.tiles` é a forma compilada; os primeiros bytes trazem o magic `tdef` seguido do nome do tileset e
do PNG de origem (`advertising_01`, `advertising_01.png`). O `.tiles.txt` é a forma legível, e é
**maior que o binário** — não é um resumo, é o mesmo dado sem compactação.

Forma do `.tiles.txt` — `PZ/media/newtiledefinitions.tiles.txt:1`:

```
version = 1
tileset
{
    file = advertising_01
    size = 8,16
    id = 88
    // advertising_01_0
    tile
    {
        xy = 0,0
        Facing = S
        Material = MetalPlates
        MaterialType = Metal_Large
        attachedFloor =
        solid =
```

`size = 8,16` é a grade do tileset em tiles; `xy = 0,0` é a posição do tile nessa grade, e é o que
gera o sufixo numérico do nome (`advertising_01_0`). Propriedade declarada sem valor
(`solid =`, `attachedFloor =`) é a forma normal do arquivo, não erro.

## Os pares não são completos

**Sete `.tiles` para cinco `.tiles.txt`.** Sem sibling de texto:

- `tiledefinitions_b42chunkcaching.tiles`
- `tiledefinitions_overlays.tiles`

Ou seja, **não presuma que existe `.tiles.txt` para todo `.tiles`** — e não presuma que editar o
`.txt` é sempre possível. Os com par são `jumbo_trees`, `jumbo_trees_big`, `newtiledefinitions`,
`tiledefinitions_erosion` e `tiledefinitions_noiseworks.patch`.

Dois arquivos relacionados moram soltos na mesma raiz e **não** seguem o padrão `.tiles`:
`tileDepthTextureAssignments.txt` e `tileGeometry.txt`.

## O TileZed gera Lua, e ele está versionado no jogo

O detalhe que não se descobre olhando a raiz de `media/`: **13 arquivos `.lua` do jogo são saída de
ferramenta**, todos em `PZ/media/lua/server/Items/`, cada um abrindo com

```lua
-- THIS FILE WAS AUTOMATICALLY GENERATED BY TileZed
```

São eles: `TileOverlays.lua`, `TileOverlaysSmooth.lua`, `CounterOverlays.lua`, `ApplianceOverlays.lua`,
`FixturesOverlays.lua`, `StorageOverlays.lua`, `SeatingOverlays.lua`, `FurnitureOfficeOverlays.lua`,
`WallsBrickOverlays.lua`, `FloorTileOverlays.lua`, `FloorStreetOverlays.lua`, `FloorWoodOverlays.lua`
e `WorldFiller.lua`.

Todos carregam uma guarda `if not TILEZED then` (`ApplianceOverlays.lua:35`,
`CounterOverlays.lua:37`, `FloorTileOverlays.lua:43`…): o mesmo arquivo é lido pelo jogo e pela
ferramenta, e o bloco final só roda fora do TileZed.

**Consequência prática:** `PZ/media/lua/server/Items/` tem 31 `.lua`, dos quais **13 são saída de
ferramenta** e 3 são a distribuição de loot (ver [distribuicao-loot.md](distribuicao-loot.md)). É uma
pasta de dado gerado, não de lógica — editar à mão ali é escrever no lugar errado.

## Os cinco arquivos-satélite de tile na raiz de `media/`

O `.tiles`/`.tiles.txt` define **quais** tiles existem. Cinco arquivos soltos na raiz de `media/`
anexam propriedades a tiles já definidos, cada um com um recorte:

| Arquivo | Tamanho | Anexa |
|---|---|---|
| `tileGeometry.txt` | 6,1 MB | forma de colisão/render por tile (`box`, …) |
| `tileDepthTextureAssignments.txt` | 1,7 MB | qual textura de profundidade cada tile usa |
| `seating.txt` | 220 KB | onde o personagem senta naquele tile (`position`) |
| `spriteModels.txt` | 76 KB | qual modelo 3D substitui o sprite |
| `seams.txt` | 52 KB | costura entre telhados vizinhos (`east`, …) |

**Quatro deles são a mesma sintaxe**, e ela não é a de `media/scripts` — sem `module`, com `VERSION`
no topo, indexada por tileset e coordenada:

```
<nomeDoBloco>
{
    VERSION = <n>,

    tileset
    {
        name = <nome do tileset>,

        tile
        {
            xy = <x> <y>,
            <propriedades>
        }
    }
}
```

Os nomes de bloco raiz são `tileGeometry` (`:1`), `seating` (`:1`), `spriteModel` — singular, ao
contrário do arquivo `spriteModels.txt` (`:1`) — e `seams` (`:1`). O `xy` aparece nas duas formas:
`0x0` em `seams.txt` e `tileGeometry.txt`, `0 0` em `seating.txt` e `spriteModels.txt`. Ambas convivem
no build atual.

`tileDepthTextureAssignments.txt` é a exceção: sem `tileset`, sem `tile`, é um mapa plano
`<tile> = <tile>` sob o `VERSION` (`:1-4`), ligando cada sprite ao sprite cuja depthmap ele reusa.

**`spriteModels.txt` é a ponte para o 3D.** Cada entrada aponta um `modelScript` para um bloco
`model` de `media/scripts` (232 ocorrências), com transformação própria:

```
        tile
        {
            xy = 0 0,
            modelScript = Base.RadioBlack_Ground,
            translate = 0.0000 0.0000 -0.1400,
            rotate = 180.0000 0.0000 180.0000,
```

(`PZ/media/spriteModels.txt:9-14`.) É por aqui que um tile de mapa vira malha — ver
[arte-e-modelos.md](arte-e-modelos.md) para o lado do bloco `model`.

### Um mod pode trazer os satélites — e eles somam, não substituem

Dois mods publicados em `STEAM/` embarcam arquivo-satélite próprio, e ambos o põem em
**`common/media/`**, na raiz da `media/` do mod (não sob `scripts/`):

| Mod | Arquivos | Linhas |
|---|---|---|
| `3403870858` *Lifestyle* | `seating.txt`, `tileGeometry.txt`, `tileDepthTextureAssignments.txt` | 182 / 2.377 / 3.810 |
| `3462962143` *Escalator* | `tileGeometry.txt`, `tileDepthTextureAssignments.txt` | 6 / 5 |

O `VERSION` que os mods declaram é **o mesmo do jogo** em todos os casos (`tileGeometry` = 2,
`seating` = 3, `tileDepthTextureAssignments` = 1), e o `tileset` referenciado é o do próprio mod
(`name = LS_Sculptures_Seating_01`).

**O `Escalator` prova que o arquivo do mod não substitui o do jogo.** Os dois que ele publica estão
*vazios* — só o cabeçalho e o `VERSION`:

```
tileGeometry
{
	VERSION = 2,

	
}
```

(`STEAM/3462962143/mods/Escalator/common/media/tileGeometry.txt:1-6`.) Se o jogo trocasse o seu
arquivo pelo do mod, ativar esse mod apagaria a geometria de **todos** os tiles do jogo — 6,1 MB de
definição. Como o mod está publicado e em uso, ou o conteúdo soma ao do jogo, ou o arquivo vazio é
ignorado; em nenhuma das duas hipóteses ele substitui. Vale a ressalva de que isto descarta a
substituição, e não prova por qual dos dois caminhos a soma acontece.

## As propriedades de `tile` — e uma divergência com a fonte externa

O PZ-API-Docs documenta as propriedades de tile em
`pz-wiki-modding.github.io/PZ-API-Docs/mapping/tile_properties.html`, com *allowed values* por
propriedade — informação que o `.tiles.txt` não dá, porque lá só se vê o que foi usado. Cruzando com
o censo de `newtiledefinitions.tiles.txt`:

- **`MoveType`** — a fonte lista `Normal`, `WallObject`, `WindowObject`, `Window`, `FloorTile`,
  `FloorRug`, `Vegitation`. O jogo usa seis deles: `WallObject` (2.056), `Window` (444), `FloorRug`
  (307), `WindowObject` (136), `FloorTile` (133), `Vegitation` (82). **`Normal` tem zero uso** —
  coerente com ser o default, mas isso é inferência.
- **`IsoType`**, **`PickUpTool`** e **`SlopedSurfaceDirection`** têm listas fechadas na fonte
  (`IsoObject`/`IsoStove`/…; `None`/`Hammer`/`Crowbar`/…; `N`/`NE`/`E`/…) e não foram censadas aqui.
- `BlocksPlacement`, `IsHigh`, `IsLow`, `UseObjectDepthTexture` são booleanos.

### Superfície e contêiner — o móvel pode ser um, outro, os dois ou nenhum

São dois eixos independentes, e a confusão entre eles custa caro em mod de loot (ver
[distribuicao-loot.md](distribuicao-loot.md), "Item em cima da mesa"):

- **`container = <tipo>`** faz o móvel ter inventário — e o valor é a chave que a tabela de loot usa
  dentro de cada sala. Censo em `PZ/media/newtiledefinitions.tiles.txt`: 1.266 tiles, sendo
  `counter` 257, `shelves` 192, `overhead` 66, `desk` 62, `fridge` 54, `wardrobe` 48.
- **`Surface = <pixels>`** faz o móvel ter tampo onde item **fica em cima**: 2.632 tiles. O
  acompanham `IsSurfaceOffset` (306, flag sem valor), `IsTableTop` (321) e `ItemHeight` (503).

Cruzando bloco a bloco no mesmo arquivo: **691 tiles têm os dois**, **1.373 têm só `Surface`** e
**575 têm só `container`**. Ou seja, a bancada da cozinha se abre *e* recebe tralha em cima; a mesa
de jantar só recebe em cima; a geladeira só se abre.

O bloco a olhar como exemplo é `appliances_com_01_0`, em `PZ/media/newtiledefinitions.tiles.txt:993`
— tem `IsSurfaceOffset`, `IsTableTop`, `ItemHeight = 20` e `Surface = 34` no mesmo `tile`.

**A altura usada de fato não é só o `Surface`.** `IsoObject.getSurfaceOffsetNoTable()` combina
`Surface`, `ItemHeight` (quando `IsSurfaceOffset` está presente) e o `renderYOffset` do objeto, e o
consumidor divide por `96` — a altura da textura 1X em pixels — para virar deslocamento de mundo
(`PZ/media/lua/server/BuildingObjects/ISPlace3DItemCursor.lua:232-234`, com o comentário do jogo
explicando a conta; a composição interna veio do bytecode, ver a mesma seção citada acima).

### Reconhecer um móvel pelo Lua — `CustomName` + `GroupName` `[levantado 2026-09-30]`

O nome que o jogador lê num móvel é a junção de duas propriedades do tile, `GroupName` e
`CustomName`, e o próprio jogo as lê assim
(`PZ/media/lua/client/ISUI/ISWorldObjectContextMenu.lua:97-100`, `props:has(…)` / `props:get(…)`;
direto no objeto em `:2953-2954`, `bed:getProperties():get("CustomName") == "Tent"`).

É a chave certa para um mod reconhecer um tipo de móvel: as quatro orientações são quatro sprites
com o **mesmo** par, e o móvel que o jogador pegou e recolocou volta com as mesmas propriedades. O
computador de mesa é o exemplo — `appliances_com_01_72` a `_75`, todos com `CustomName = Computer`
e `GroupName = Desktop`, um por `Facing` (`PZ/media/newtiledefinitions.tiles.txt:2091-2156`).
Comparar nome de sprite obriga a listar os quatro.

### `CustomItem` — o tile vira item, mas só num sentido `[levantado 2026-10-31]`

Um tile com `CustomItem = Modulo.Item` vira esse item quando é pego como móvel. Em vez do
`Moveables.<sprite>` genérico, `ISMoveableSpriteProps:instanceItem` faz `instanceItem(self.customItem)`
(`PZ/media/lua/shared/Moveables/ISMoveableSpriteProps.lua:214-219`). O caso do botijão:
`industry_03_105` e as variantes dele, com `CustomName = Propane Tank` e
`CustomItem = Base.PropaneTank` (`PZ/media/newtiledefinitions.tiles.txt:97591-97598`). Isso tem duas
consequências que falham em silêncio:

- **O item sai novo.** `pickUpMoveableInternal` chama `self:instanceItem(...)`
  (`ISMoveableSpriteProps.lua:1376-1383`), e um *drainable* sai cheio. O estado do objeto não passa
  para o item, salvo o que `GameEntityFactory.TransferComponents` carrega (`:1383`).
- **O caminho inverso não existe.** Colocar um móvel procura um item `instanceof(item, "Moveable")`
  (`:1571`). `Base.PropaneTank` é *drainable* e não tem `WorldObjectSprite`
  (`PZ/media/scripts/generated/items/drainable.txt:1578-1593`), então não se coloca de volta.

### `Facing` — o código contradiz a fonte

A fonte declara *"Allowed values: `North`, `East`, `South`, `West`"*. O jogo escreve **letra única**,
em 6.196 ocorrências e sem uma só exceção:

```
2160 Facing = S
1930 Facing = E
1089 Facing = N
1017 Facing = W
```

(censo em `PZ/media/newtiledefinitions.tiles.txt`; a forma aparece também no recorte do topo desta
página, `Facing = S`.) **Escreva a letra.** Pela regra da árvore, em divergência o código ganha —
e aqui não é margem de interpretação: a forma por extenso não ocorre nenhuma vez. Se o parser
aceita as duas, é irrelevante para quem escreve, porque a forma comprovada é uma só.

Isso vale como aviso sobre a seção **mapping** da fonte em geral: ela é a única referência de
*allowed values* de tile que existe, e ao mesmo tempo já errou num campo de alta frequência. Trate
cada lista como candidata a confirmar, não como contrato — ver
[fontes-externas.md](../fontes-externas.md).

## Um mod que traz tileset próprio `[levantado 2026-11-01]`

Três peças, todas necessárias:

- `mod.info` com `pack=<nome>` e `tiledef=<nome> <número>` — o número tem de ficar entre 100 e
  8189 (erro de `ChooseGameInfo.readModInfoAux` em [testar-e-debugar.md](testar-e-debugar.md));
- `common/media/<nome>.tiles` (binário do TileZed; o `.tiles.txt` ao lado é opcional);
- `common/media/texturepacks/<nome>.pack`.

Exemplo publicado: `STEAM/3596827035/mods/ShelterHold_Beehive/42/mod.info` (`pack=Hold_BeehiveTiles`,
`tiledef=Hold_BeehiveDef 7924`), com `common/media/Hold_BeehiveDef.tiles` e
`common/media/texturepacks/Hold_BeehiveTiles.pack`. O número do `tiledef` compõe o ID dos sprites e
**colide** entre mods: censo de `STEAM/` em 2026-11-01 — 0216, 0217, 0218, 222, 446, 500, 515, 714,
999, 1122–1125, 1234, 1235, 3333, 3452, 4242–4244, 4729, 5520, 5620, 6985, 7001, 7924, 9476 (o 9476
está fora da faixa válida e aparece mesmo assim).

## Sprite por cima de um objeto: overlay × attached `[levantado 2026-11-01, javap no .jar]`

`zombie.iso.IsoObject` tem dois mecanismos:

- **`setOverlaySprite(nome, r, g, b, a)`** — slot **único**. Já é usado pela placa pintada
  (`PZ/media/lua/shared/BuildingObjects/TimedActions/ISPaintSignAction.lua:35`); um mod que escreva
  nele apaga o que estava.
- **Lista de attached sprites** — `AttachExistingAnim(sprite, 0, 0, false, 0, false, 0.0)`
  (`PZ/media/lua/server/ClientCommands.lua:187`), `RemoveAttachedAnim(índice)` 0-based
  (`ClientCommands.lua:103`), iteração por `getAttachedAnimSprite()` +
  `inst:getParentSprite():getName()`
  (`PZ/media/lua/client/DebugUIs/DebugChunkState/DebugChunkState_ObjectProperties.lua:126-134`).
  Vários convivem no mesmo objeto.

**O attached vai para o save**: `IsoObject.save` grava o ID de cada instância, e `IsoObject.load`
resolve por `IsoSprite.getSprite(manager, id)` com checagem de nulo depois. Sprite anexado precisa
então ser de tileset registrado (ID estável); `IsoSprite.new()` + `LoadSingleTexture`, o caminho
do cursor de construção (`PZ/media/lua/server/BuildingObjects/ISBuildingObject.lua:552-555`), não
tem ID de tileset.

Vida do objeto como razão: `getThumpCondition()` da interface
`zombie.iso.objects.interfaces.Thumpable` devolve `clamp(health, 0, max) / max` em `IsoDoor`,
`IsoWindow` e `IsoThumpable`. É a única forma uniforme: `IsoWindow` tem `maxHealth` **privado**,
sem `getMaxHealth()`, e não implementa `IHasHealth` (que `IsoDoor`, `IsoThumpable` e `IsoBarricade`
implementam). Parede do mapa é `IsoObject` sem vida.

## Pontos a confirmar

- **Se `getThumpCondition()` é chamável do Lua.** Público em classe exposta, mas zero chamadas em
  `media/lua`.
- **O que acontece no load com attached sprite de tileset que sumiu** (mod removido). O bytecode
  sugere que o nulo é pulado; não testado in-game.

- Qual dos três artefatos o jogo lê em runtime — se o `.tiles` binário torna o `.tiles.txt`
  dispensável na distribuição de um mod, ou se ambos precisam ir junto. Os dois `.tiles` sem par de
  texto sugerem que o binário basta, mas isso é inferência.
- **Por qual mecanismo o satélite de mod soma ao do jogo.** Que ele **não substitui** está
  confirmado (seção acima); se o motor concatena as entradas, se indexa por `tileset` e só consulta o
  arquivo do mod para os tilesets dele, ou se lê os arquivos em ordem e o último a declarar um `xy`
  vence, não é decidível no `media/`. Importa quando um mod quiser reescrever a geometria de um tile
  **do jogo**, e não só a dos seus.
- **Nenhum mod traz `spriteModels.txt` nem `seams.txt`** — os dois observados cobrem só `seating`,
  `tileGeometry` e `tileDepthTextureAssignments`. Que os outros dois funcionem igual é extrapolação
  pela sintaxe compartilhada, não observação.
- **As duas formas de `xy`** (`0x0` e `0 0`) — se o parser aceita as duas em qualquer um dos quatro
  arquivos, ou se cada bloco tem a sua. O uso observado é consistente por arquivo, o que não
  distingue as duas hipóteses. O `seating.txt` do *Lifestyle* usa `0 0`, a mesma forma do
  `seating.txt` do jogo, então o mod não testa a hipótese.
- **Se `tileGeometry.txt` é lido pelo mesmo parser do bloco `tileGeometry` que o PZ-API-Docs lista**
  no índice de `scripts` (ver [fontes-externas.md](../fontes-externas.md)). Nome igual, arquivo em
  raiz diferente, sintaxe da família de tile e não a de `media/scripts`.
- Se o TileZed ainda é a ferramenta corrente no B42 e onde obtê-la — não há binário nem link em
  `PZ/`. Os arquivos gerados provam que foi usada, não que ainda seja.
- Formato interno do `.pack` e como um tileset novo entra num pack. Nada em `media/lua` monta `.pack`.
- Lista completa de propriedades válidas de `tile` no `.tiles.txt`. A seção **mapping** do
  PZ-API-Docs é a única fonte que as enumera com *allowed values* (seção acima), mas **erra em
  `Facing`**, o que a desqualifica como contrato. As de `advertising_01` são amostra de um tileset,
  não o conjunto; um censo próprio é caro, porque o arquivo tem 6,8 MB.
- **`IsoType` e `PickUpTool`: censados.** Os valores **em uso** nos `.tiles.txt` da raiz de `media/`:

  | `IsoType` | Ocorrências | | `PickUpTool` | Ocorrências |
  |---|---|---|---|---|
  | `IsoStove` | 54 | | `Hammer` | 1.655 |
  | `IsoRadio` | 48 | | `Crowbar` | 573 |
  | `IsoBarbecue` | 33 | | `Electrician` | 219 |
  | `IsoFireplace` | 24 | | `Shovel` | 203 |
  | `IsoFeedingTrough` | 16 | | `Screwdriver` | 84 |
  | `IsoMannequin` | 13 | | `Cutter` | 57 |
  | `IsoTelevision` | 12 | | `Wrench` | 54 |
  | `IsoCompost`, `IsoCombinationWasherDryer`, `IsoClothingWasher`, `IsoClothingDryer`, `IsoBrokenGlass` | 4 cada | | | |

  Vale a mesma ressalva das 57 flags de [scripts-txt.md](scripts-txt.md): **isto é o conjunto usado,
  não o aceito pelo parser.** `IsoType` casa com nomes de classe Java (`IsoStove`, `IsoRadio`), o que
  sugere que o conjunto válido é fechado e definido lá; `PickUpTool` parece nome livre de ferramenta.
  Nenhum dos dois foi cruzado contra o PZ-API-Docs, que erra em `Facing` e por isso não serve de
  desempate.

- **`SlopedSurfaceDirection` não é censável por texto.** A única ocorrência em todo o `media/` está
  em `PZ/media/tiledefinitions_b42chunkcaching.tiles` — **o arquivo binário**, que não tem par
  `.tiles.txt` (a página já registra que os pares são incompletos). Zero ocorrências em qualquer
  `.tiles.txt`, `.txt` ou `.lua`. Ou seja, a propriedade existe no build mas nenhum tileset em forma
  de texto a usa; os *allowed values* só sairiam do binário ou do Java.
